# RFC-0004: Internationalization (i18n) for the UI

- **Status:** Draft
- **Related module:** all of `src/components/*.tsx` (strings currently hardcoded inline
  in Vietnamese).
- **Not related to RFC-0003:** i18n is purely a Layer 3 (Applications/UI) concern — it
  never touches Identity/Proof/Reputation at Layer 2. Display language is a
  device/browser preference, not portable data tied to an npub — deliberately NOT stored
  in a Nostr profile or any proof (see State Storage below).

## Problem

Every display string currently sits directly inside each component's JSX (`"Lưu Trú"`,
`"Đồng ý"`, `"Xác nhận trả phòng [...]?"`...) — hardcoded Vietnamese, not separated from
logic. Adding an English version means editing every component, and every new string has
to be manually kept in sync across both versions, which drifts over time. A mechanism to
pull strings out of components is needed before the number of components grows further
and makes this many times more expensive to fix later.

## Alternatives considered

### Option A: Full `react-i18next` library
- Pros: industry standard, supports complex pluralization/interpolation/namespacing, big
  community, easy to onboard devs already familiar with it.
- Cons: adds a dependency + configuration (i18next-browser-languagedetector, Suspense
  loading...) beyond current real needs — most strings in the app don't need complex
  pluralization or advanced interpolation.

### Option B: A minimal, hand-written dictionary + a `useTranslation()` hook
- Pros: no new dependency, enough for every string that currently exists (mostly static
  text + a few simple interpolations like `${listingTitle}`), easy to understand, easy to
  fully audit in a few minutes.
- Cons: if proper pluralization is needed later (e.g. "1 night" vs "2 nights" vs the
  Vietnamese equivalent which doesn't pluralize the same way) or RTL support for another
  language, that has to be hand-built instead of coming for free.

### Option C: Two entirely separate component trees (an EN app / a VI app)
- Pros: none.
- Cons: directly violates the same "evolve by addition, not replacement" principle from
  RFC-0003 — doubles maintenance work, the two trees will inevitably drift. Rejected.

### Option D: Runtime translation via a third-party API (Google Translate, etc.)
- Pros: no manual translation needed.
- Cons: **violates the "no backend" principle** — depends on an external service on every
  render, uncontrolled translation quality, costs money, doesn't work offline. Rejected.

## Proposal

**Option B** for the current stage — the app's scale doesn't yet need Option A's power.
Explicitly noted in this RFC: if pluralization/multi-language complexity later exceeds
what a hand-written dictionary can handle, upgrade to Option A via a separate RFC — don't
treat today's decision as permanent (same "not yet frozen" spirit as RFC-0003).

### Structure

```
src/locales/
  vi.json   — SOURCE OF TRUTH — the team thinks/designs in Vietnamese
  en.json   — first translation
src/hooks/useTranslation.ts  — hook reading the current locale from context, returns t(key)
```

Keys namespaced by feature, not by component (so refactoring UI doesn't force key
renames): `booking.confirmCheckout`, `governance.voteApprove`, `deposit.hostClaimWindow`...
— consistent with how `proof_type` is namespaced in RFC-0003.

### Language State Storage

A dedicated `localStorage` key (`cypherguide_locale`), **not** tied to `NostrIdentity`,
never placed into any Nostr proof/event — switching browsers means picking the language
again, which is the correct behavior since language isn't identity.

## Migration Path (no big-bang rewrite)

1. Set up empty `vi.json`/`en.json` + the `useTranslation()` hook — no component changes yet.
2. Migrate in groups, prioritizing what users see first: `AppLayout.tsx` (tab labels) →
   the booking flow (`ListingDetail.tsx`) → everything else.
3. Once a component is migrated, remove its hardcoded Vietnamese strings — don't keep both
   approaches side-by-side in the same file for long (confuses where the real source
   string lives).
4. Once ≥80% of components use `t()`, add a language switcher UI (in
   `NostrIdentityManager.tsx` or the header) — not needed before that, since the
   translation wouldn't be complete enough to switch without exposing gaps.

## Trade-offs

Much lower risk than the earlier security RFCs — no money, no identity involved. The main
risk is maintenance cost (forgetting to update `en.json` when adding a string to
`vi.json`) — mitigated later by a simple lint rule (warn if `en.json` is missing a key
present in `vi.json`), not needed yet at this Draft stage.

## Proposed maturity tier after implementation

**Experimental** until stages 2-3 of the migration path are done (most components
migrated). Key naming can change freely before that; once the language switcher appears
(stage 4) and real users start using it, renaming a key namespace becomes a breaking
change, requiring the same care as changing a Nostr tag under RFC-0003.
